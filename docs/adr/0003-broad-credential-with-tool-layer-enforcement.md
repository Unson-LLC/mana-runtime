# 広権限クレデンシャル+ツール層強制を許容する条件

**日付**: 2026-07-30（Google Drive接続の設計討議より。実装は未着手）

## Context

外部サービス（例: Google Drive）へmanaを接続する際、アクセス権の設計は2通りある:

1. **専用アカウント方式**: mana専用アカウントに必要フォルダだけを共有。アクセス制御の正本はサービス側の共有設定
2. **広権限+設定制限方式**: manaが広い権限のクレデンシャルを持ち、placement設定でアクセス範囲を絞る

placementが増える運用では、(2)の「範囲追加が config 1行・レビュー履歴つき」という管理性が勝る。ただし範囲制限をプロンプト（dataScopes）にだけ書くと、インジェクション一発で全権が露出する。

## Decision

広権限クレデンシャル方式は、以下**すべて**を満たす場合に限り許容する:

1. クレデンシャルは**gateway所有のツール層（MCPプロキシ）だけが保持**し、モデル・子プロセスへ渡さない
2. 範囲制限（フォルダ許可リスト等）は**ツール層がリクエストごとにコードで検査**する（deny-by-default。Driveならファイル→祖先フォルダ解決→許可リスト交差必須。ショートカット・共有アイテム直下も塞ぐ）
3. スコープは最小で発行（例: `drive.readonly`）。書込は別リストで明示昇格
4. 拒否は `security_event` に記録する

## Why

- ADR-0001の原則（制限はハード境界で強制）の適用。ツール層で決定論的に検査すれば、設定の管理性と境界の強さを両立できる
- 専用アカウント方式は漏えい時の被害が小さい反面、placementごとの出し分けにアカウント増設が要り、運用がスケールしない

## Alternatives

- 専用アカウント方式: placementが少ないうち、またはツール層検査を実装できないサービスでは引き続き有効な選択肢
- domain-wide delegation（発話者本人の権限で代行): 権限モデルとしては最も正確だが、Workspace管理・ユーザー対応付けが重い。参加者ごとの出し分け要件が出てから再検討

## Consequences

- 弱点は「クレデンシャル自体の漏えい=全権露出」。ツール層の外へ出さない実装regressionをレビュー観点に含める（[08_security_design.md](../architecture/08_security_design.md) §4）
- 祖先解決の抜け（マルチペアレント・ショートカット）は権限バイパスに直結する。実装時はここをテスト必須にする
