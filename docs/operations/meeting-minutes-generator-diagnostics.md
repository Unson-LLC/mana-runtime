# 議事録生成の実行結果を診断する

## SDKとの境界

議事録生成は `generateMeetingMinutesInSandbox` でCloudflare Sandboxの実行結果を受け取る。SDKは実行時間をミリ秒の `duration` で返す。`outcome` と `elapsedMs` は既存adapterの追加項目であり、SDKから必ず返る項目ではない。

診断の実行時間は、有効な `duration`、既存adapterの有効な `elapsedMs`、生成開始から終了までの壁時計の順に採用する。壁時計への代替はSandbox準備時間も含むため、SDKの実行時間とは区別する。

期限切れの分類は、明示的な `outcome=timeout`、または終了コード124と設定期限以上のSDK実行時間が両方ある場合に行う。124だけ、実行時間の欠測・不正値、期限前の終了では期限切れと断定しない。この分類は待ち時間の消費を示すもので、モデル、認証先、コンテナのどこが停止を起こしたかを証明しない。

## 回帰を防ぐ検証

`packages/cloud-runtime/src/__tests__/meeting-minutes-generation-observability.test.ts` はSDKと同じ結果形式を使用し、次を検証する。

- SDKの実行時間を診断へ保持する。
- 期限に達した終了コード124を期限切れとして扱う。
- 期限前の124、実行時間の欠測や不正値で原因を確定しない。
- 既存adapterの明示的な期限切れ、例外、出力の秘匿を維持する。

テスト専用の追加項目だけでSDKとの接続を検証したことにしない。`stdout`、`stderr`、プロンプト、コマンド、認証情報を診断記録へそのまま保存しない。

## 本番で分けて確認するもの

2026年9月6日の失敗実行では、文脈取得成功後、約13分で終了コード124となり、最終生成結果を観測できなかった。従来の診断にはSDKの実行時間が保持されず、停止の発生源は確定できていない。

通常の返信処理の管理プロセス監視と稼働時間設定は、議事録生成には適用されていない。これらの差だけで原因を決めず、同じ実行器の短い固定入力と対象入力で、起動・最初の出力・最終結果を比較する必要がある。

配備・ヘルスチェック、生成、GitHub保存、Slack共有、タスク登録はそれぞれの実結果で確認する。診断修正やテスト成功を、生成停止の解消と扱わない。
