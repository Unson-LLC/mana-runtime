# ポリシー駆動書き込み承認のアーキテクチャ

## 決定

署名付きcapability、実行時ポリシー、予算、承認、監査を別の責務として扱う。capabilityは「可能な操作の上限」、ポリシーは「今回どう扱うか」を表し、両方が許可し、予算を確保できた場合だけ実行へ進む。

## 責務境界

- 共通タスクコア: Canonical Taskの操作契約、プロジェクト制約、冪等性を所有する。
- capability層: 依頼者、配置先、プロジェクト、操作、対象、期限、再利用防止を改ざん不能に運ぶ。
- ポリシー層: 依頼者と操作の文脈を評価し、`auto`、`approval`、`deny`の判断を返す。既定値は拒否とする。
- 予算層: 上限評価と、実行前の予約、確定、解放を所有する。
- write broker: 各判断を組み合わせ、保留または実行を調停する。個別業務の正本にはならない。
- 承認adapter: Slackなどの操作面を提供する。保留内容の正本や実行権限を所有しない。
- 監査adapter: 判断と実行のreceiptを追記専用で保存する。

## 正本

- 業務データ: Brainbase Canonical Task
- 書き込みルール: version付きポリシー設定
- 保留中の依頼: brokerの永続状態
- 予算消費: 予算層の予約記録
- 判断・実行履歴: 追記専用receipt
- Slackメッセージ: 表示と入力の投影であり正本ではない

## 判断の流れ

1. transportが安定した依頼者IDとworkspaceを渡す。
2. capability層が改ざん、期限、配置先、プロジェクト、操作、対象を検証する。
3. ポリシー層が依頼文ではなく構造化済みの対象を評価する。
4. `deny`は実行せずreceiptを残す。
5. `approval`は入力内容を固定して保留し、承認adapterへ投影する。
6. `auto`または有効な承認再開は、予算を予約してから業務adapterを呼ぶ。
7. 結果に応じて予算を確定または解放し、receiptを追記する。

## 不変条件

- 表示名を依頼者識別に使わず、provider・workspace・user IDの組を使う。
- プロジェクトを自然言語だけから推測しない。配置先の信頼済み範囲と対象IDから確定する。
- 承認後に入力内容を再生成しない。保留時に固定した内容と同一のものだけを実行する。
- 承認は単回使用で、期限切れ、二重操作、権限変更、ルール変更をfail closedにする。
- wildcardで露出した書き込みツールがbrokerを迂回できないよう、書き込みは共通境界を必ず通す。
- capability、ポリシー、予算のいずれかが拒否なら自動実行しない。

## 段階展開

最初はTask作成・更新だけを対象に、shadow判定で実判断との差を観測する。その後、限定Placementで低リスクの`auto`を有効にし、`approval`は共通保留契約が安定してからSlack adapterへ接続する。
